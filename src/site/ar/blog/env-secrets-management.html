كيف تخزّن متغيرات البيئة والأسرار بأمان

أغسطس 2025 قراءة 8 دقائق بقلم فريق Zecure

يفحص GitHub المستودعات العامة بحثًا عن الأسرار المسرّبة، وقد عثر على الملايين منها. ملف .env واحد يُرفع بالخطأ قد يكشف قاعدة بياناتك وبيانات مستخدميك وفاتورة خدماتك السحابية. إليك دليل المطوّر للقيام بذلك بالطريقة الصحيحة، من التطوير المحلي حتى بيئة الإنتاج.

المشكلة: الأسرار ينتهي بها المطاف في Git

أكثر طرق تسريب مفاتيح API شيوعًا بسيطة: يضع المطوّر بيانات الاعتماد في ملف .env، وينسى إضافة .env إلى .gitignore، ثم يرفع التغييرات إلى GitHub. أو يكتب سرًّا مباشرة في الشيفرة المصدرية أثناء اختبار سريع ولا يحذفه أبدًا. أو يستخدم متغيرات البيئة داخل ملف إعدادات CI/CD يُرفع إلى المستودع.

بمجرد أن يظهر السرّ في commit داخل git، حتى لو حذفته فورًا، يبقى محفوظًا في سجل المستودع. أي شخص ينسخ المستودع يستطيع تشغيل git log والعثور عليه. وتجوب الروبوتات GitHub باستمرار بحثًا عن مفاتيح API وبيانات اعتماد قواعد البيانات والمفاتيح الخاصة.

إذا رفعت سرًّا عن طريق الخطأ: اعتبره مكشوفًا. غيّر المفتاح فورًا، ولا تنتظر لتتحقق مما إذا كان أحد قد عثر عليه؛ فالروبوتات تفحص GitHub في غضون دقائق. إعادة كتابة سجل git ليست بديلًا عن تغيير بيانات الاعتماد.

نهج المستويات في تخزين الأسرار

لا يوجد حل واحد يناسب كل الحالات. الأداة المناسبة تعتمد على مكان وجود السرّ ومن يحتاج إلى الوصول إليه:

أبدًا
مكتوب مباشرة في الشيفرة
أسرار داخل ملفات .js أو .py أو ملفات إعدادات مرفوعة إلى نظام التحكم بالإصدارات. مكشوفة فورًا.
للتطوير فقط
ملف .env (مُستثنى عبر gitignore)
مناسب للتطوير المحلي. لا يُستخدم أبدًا في الإنتاج. أضف .env إلى .gitignore قبل أول commit.
مقبول
متغيرات بيئة المنصة
توفّر Vercel وRailway وRender وHeroku جميعها تخزينًا لمتغيرات البيئة السرية. أفضل من ملف .env، لكن راجع صلاحيات الوصول بعناية.
للإنتاج
مدير الأسرار
AWS Secrets Manager وGCP Secret Manager وHashiCorp Vault. مع سجل تدقيق، وإمكانية تدوير الأسرار، والتحكم في الوصول.

إعداد ملف .env الصحيح للتطوير المحلي

في التطوير المحلي، ملفات .env هي المعيار المتّبع. والقواعد بسيطة:

# .gitignore — أضف هذا قبل أول commit
.env
.env.local
.env.*.local

# ارفع قالبًا فقط — لا قيمًا حقيقية أبدًا
.env.example
# .env.example — يُرفع إلى git ويعرض المتغيرات المطلوبة دون قيم حقيقية
DATABASE_URL=postgresql://user:password@host:5432/dbname
STRIPE_SECRET_KEY=sk_live_...
JWT_SECRET=replace-with-64-random-chars
AES_KEY=replace-with-64-hex-chars

ارفع الملف .env.example (بقيم وهمية) ليكون توثيقًا. ينشئ كل مطوّر ملف .env المحلي الخاص به بالقيم الحقيقية. هذا الملف لا يُرفع أبدًا.

تحقّق من .gitignore قبل الرفع

# تحقّق مما إذا كان git سيتتبّع ملف .env
git check-ignore -v .env

# إذا لم يُرجع شيئًا، فملف .env غير مُستثنى — أصلح ذلك قبل الـ commit
echo ".env" >> .gitignore

CI/CD: حيث تنكشف الأسرار عادةً

تحتاج خطوط CI/CD إلى الأسرار لإتمام النشر: روابط قواعد البيانات، وبيانات اعتماد الخدمات السحابية، ومفاتيح API. والأساليب الخاطئة شائعة:

# خطأ — القيمة مكتوبة مباشرة في ملف الـ workflow
env:
  DATABASE_URL: postgresql://admin:hunter2@prod-db:5432/app

# صحيح — الإشارة إليها من مخزن أسرار المنصة
env:
  DATABASE_URL: ${{ secrets.DATABASE_URL }}

توفّر GitHub Actions وGitLab CI وCircleCI جميعها مخازن أسرار مشفّرة. لا تضع القيم الحقيقية أبدًا في ملفات YAML الخاصة بالـ workflow. أشِر إلى الأسرار بأسمائها، وستحقن المنصة القيمة أثناء التشغيل دون أن تظهر في السجلات أو في السجل التاريخي.

انتبه لأوامر echo في سجلات CI. إذا نفّذت بالخطأ echo $DATABASE_URL في إحدى خطوات CI، فقد يظهر السرّ في سجلات البناء، وهي غالبًا متاحة للجميع في المستودعات العامة. راجع مخرجات السجل دائمًا بعد إضافة خطوات تصحيح الأخطاء.

الإنتاج: استخدم مدير أسرار

في أعباء العمل الإنتاجية، تكفي متغيرات البيئة التي تحقنها المنصة لعمليات النشر البسيطة، لكن مدير الأسرار المخصص هو الإجابة الصحيحة لأي شيء مهم:

AWS Secrets Manager

// Node.js — اجلب السرّ أثناء التشغيل، لا أثناء النشر
import { SecretsManagerClient, GetSecretValueCommand } from '@aws-sdk/client-secrets-manager';

const client = new SecretsManagerClient({ region: 'us-east-1' });

const secret = await client.send(new GetSecretValueCommand({
  SecretId: 'prod/myapp/database'
}));
const { DB_PASSWORD } = JSON.parse(secret.SecretString);

HashiCorp Vault

# Vault CLI — قراءة سرّ
vault kv get secret/myapp/prod

# يجلب التطبيق الأسرار عند بدء التشغيل عبر Vault API
# يُتحكَّم في الوصول عبر سياسات Vault المرتبطة بهوية التطبيق

المزايا الأساسية لمدير الأسرار مقارنةً بمتغيرات بيئة المنصة: التدقيق (من وصل إلى ماذا، ومتى)، والتدوير (حدّث السرّ في مكان واحد فتحصل عليه جميع التطبيقات)، والتحكم في الوصول (لا تحصل التطبيقات إلا على الأسرار التي تحتاجها، لا على كل شيء).

توليد أسرار تستحق الحماية

مدير الأسرار عديم الفائدة إذا كانت الأسرار نفسها ضعيفة. كل سرّ في بنيتك التحتية، من كلمات مرور قواعد البيانات إلى مفاتيح توقيع JWT ومفاتيح التشفير، يجب أن يكون:

  • مولَّدًا بواسطة CSPRNG (مولّد أرقام عشوائية آمن تشفيريًا)، لا مكتوبًا بيد إنسان
  • بإنتروبيا (مقدار العشوائية) لا تقل عن 128 بت (32 حرفًا عشوائيًا أو أكثر من مجموعة أحرف كبيرة)
  • فريدًا لكل بيئة (التطوير والاختبار والإنتاج، لكلٍّ منها قيم مختلفة)
  • يُغيَّر عندما يغادر عضو في الفريق كانت لديه صلاحية الوصول
// Node.js — توليد سرّ بطول 256 بت لتوقيع JWT أو تشفير AES
const { randomBytes } = require('crypto');
console.log(randomBytes(32).toString('hex'));
// → 64 حرفًا ست عشريًا (256 بت). الصقه في مدير الأسرار.

قائمة التحقق

  • ملف .env موجود في .gitignore: تحقّق بالأمر git check-ignore -v .env قبل أول رفع
  • ملف .env.example مرفوع: يوثّق المتغيرات المطلوبة دون قيم حقيقية
  • أسرار CI في مخزن المنصة: أسرار GitHub Actions، لا قيم مكتوبة مباشرة في YAML
  • بيئة الإنتاج تستخدم مدير أسرار: مع التدقيق والتدوير
  • كل سرّ فريد لكل بيئة: الإنتاج والاختبار يستخدمان قيمًا مختلفة
  • الأسرار مولَّدة عشوائيًا: غير مشتقة من أسماء أو تواريخ أو عبارات سهلة التذكر
  • توجد خطة للتدوير: اعرف كيف ومتى تُغيّر كل سرّ

ولّد أسرارًا تستحق الحماية

احصل فورًا على مفاتيح API وأسرار JWT ومفاتيح AES عشوائية تشفيريًا، تُولَّد محليًا داخل متصفحك ولا تُرسَل أبدًا إلى أي خادم.
