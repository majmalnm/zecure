مفاتيح API مقابل كلمات المرور: ما الفرق؟

فبراير 2025 قراءة 6 دقائق بقلم فريق Zecure

مفاتيح API ليست كلمات مرور، ومعاملتهما بالطريقة نفسها من أكثر الأخطاء الأمنية شيوعًا بين المطوّرين. فلكلٍّ منهما صيغة مختلفة، ومتطلبات تخزين مختلفة، واستراتيجية تبديل مختلفة، ونموذج تهديدات مختلف.

الإجابة المختصرة

كلمة المرور تثبت هوية إنسان أمام نظام ما. تُكتب وتُحفظ في الذاكرة، وتُطبَّق عليها دالة التجزئة على الخادم قبل تخزينها. أما مفتاح API فيثبت هوية آلة (الكود الخاص بك) أمام خدمة ما. لا يُكتب يدويًا ولا يُحفظ في الذاكرة، ولا ينبغي تجزئته أبدًا، إذ يجب تخزينه وإرساله كما هو.

كلمة مرور (مصادقة الإنسان)
correct-horse-battery-staple-77
مفتاح API (مصادقة الآلة)
sk-a3f2b1c8d4e9f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5

يستخدمه البشر الكود / الآلات
الصيغة سلسلة يسهل تذكّرها قيمة عشوائية بصيغة hex / base64
الطول المعتاد 12–30 حرفًا 32–64 حرفًا أو أكثر
التخزين على الخادم مُجزّأة (bcrypt/Argon2) بادئة مع تجزئة، أو مشفّر
التخزين لدى العميل في الذاكرة فقط، لا على القرص أبدًا مدير أسرار / متغيرات بيئة
داخل الكود المصدري أبدًا أبدًا
الإرسال في جسم طلب HTTPS POST في ترويسة Authorization عبر HTTPS
التبديل عند الاشتباه في تسريبها وفق جدول منتظم + عند انكشافه
دعم المصادقة متعددة العوامل (MFA) نعم، ويُنصح به بشدة لا، ويُعوَّض ذلك بالصلاحيات المحددة + قائمة عناوين IP المسموح بها
النطاق / الصلاحيات عادةً كل شيء أو لا شيء لكل حساب دقيقة (قراءة فقط، كتابة، إلخ)

كيف تُولَّد مفاتيح API

مفتاح API السليم ليس إلا سلسلة طويلة من البايتات العشوائية الآمنة تشفيريًا، تُرمَّز عادةً بصيغة hex أو base64. أما البادئات مثل "sk-" أو "pk-" التي تستخدمها خدمات كثيرة فهي مجرد أعراف تساعد المستخدمين على تمييز نوع المفتاح، ولا علاقة لها بالأمان.

// Node.js — توليد مفتاح API على طريقة OpenAI/Stripe
const { randomBytes } = require('crypto');

function generateApiKey(prefix = 'sk') {
  const raw = randomBytes(32).toString('base64url');
  return `${prefix}_${raw}`;
}

generateApiKey(); // → "sk_A3f2B1c8D4e9F0a1B2c3..."
generateApiKey('pk'); // → مفتاح عام/قابل للنشر

الإنتروبيا (مقدار العشوائية) تأتي بالكامل من randomBytes(32)، أي 256 بت. أما البادئة والترميز فشكليان. بعض الخدمات تستخدم UUID كمفاتيح API؛ وهذا يعمل لكنه لا يوفر سوى نحو 122 بت من الإنتروبيا (UUID الإصدار 4). استخدم 32 بايت عشوائيًا أو أكثر في الأنظمة الجديدة.

الخطأ الأكبر: رفع المفاتيح إلى Git

كل شهر يعثر باحثو الأمن على آلاف مفاتيح API الصالحة التي رُفعت بالخطأ إلى مستودعات GitHub العامة. يفحص GitHub نفسه صيغ المفاتيح الشائعة ويُبلغ مزوّدي الخدمات، لكن هذا لا يعمل إلا إذا كان المزوّد قد سجّل نمط مفاتيحه. وبمجرد أن يدخل المفتاح سجل git يبقى فيه إلى الأبد، حتى لو حذفت الملف.

إذا رفعت مفتاح API بالخطأ، فبدّله فورًا. لا تكتفِ بحذف الملف أو الكتابة فوقه. افترض أن المفتاح قد تسرّب بالفعل، فالبرامج الآلية تفحص GitHub خلال ثوانٍ من أي عملية push.

# خطأ — مفتاح مكتوب مباشرة في الكود المصدري
OPENAI_API_KEY="sk-abc123..."  # ❌ لا تفعل هذا أبدًا

# صحيح — الإشارة إليه عبر متغير بيئة
OPENAI_API_KEY=os.environ["OPENAI_API_KEY"]  # ✓

# الأفضل — استخدم مدير أسرار
# AWS: boto3 secrets manager
# GCP: Secret Manager API
# HashiCorp Vault, Doppler, Infisical

تخزين مفاتيح API على الخادم

عندما تُصدر خدمتك مفاتيح API لعملائها، تواجه معضلة في التخزين. وعلى خلاف كلمات المرور، أمامك خياران:

الخيار أ: تخزين التجزئة فقط (كما في كلمات المرور)

طبّق SHA-256 على المفتاح كاملًا (لا حاجة إلى bcrypt، فمفاتيح API عالية الإنتروبيا أصلًا) وخزّن التجزئة فقط. يُعرض المفتاح على المستخدم مرة واحدة عند إنشائه. وفي كل مصادقة لاحقة تُعاد تجزئة المفتاح المقدَّم وتُقارن بالمخزَّن. العيب: لا يستطيع المستخدمون استرجاع مفتاح مفقود، بل عليهم استبداله بمفتاح جديد.

الخيار ب: تخزين البادئة + التجزئة

خزّن أول 8 أحرف كنص صريح لتمييز المفتاح لدى المستخدم (مثلًا لتعرض "sk_A3f2...")، إضافة إلى تجزئة المفتاح كاملًا. هذا هو نمط Stripe، وهو يوازن بين سهولة الاستخدام والأمان.

// إنشاء مفتاح API جديد — على الخادم
const { randomBytes, createHash } = require('crypto');

function createApiKey() {
  const raw = randomBytes(32).toString('base64url');
  const key = `sk_${raw}`;
  const hash = createHash('sha256').update(key).digest('hex');
  const prefix = key.slice(0, 10); // "sk_A3f2B1c8"

  // خزّن البادئة + التجزئة في قاعدة البيانات، وأعد المفتاح كاملًا للمستخدم مرة واحدة
  db.store({ prefix, hash });
  return key; // يُعرض على المستخدم مرة واحدة فقط
}

التبديل وتحديد النطاق

ينبغي تبديل مفاتيح API بانتظام، لا عند تسريبها فقط. الممارسات الموصى بها:

  • فترة التبديل: 90 يومًا لمفاتيح بيئة الإنتاج، وفورًا بعد مغادرة أي عضو في الفريق
  • أقل نطاق ممكن: أصدر مفاتيح منفصلة للقراءة فقط لأغراض المراقبة، ومفاتيح كتابة للنشر، ولا تستخدم مفتاحًا واحدًا لكل شيء
  • قائمة عناوين IP المسموح بها: إذا كانت خدمتك تدعم ذلك، فاقصر استخدام المفاتيح على عناوين IP الخاصة بخوادمك
  • انتهاء صلاحية المفاتيح: حدّد مدة صلاحية (TTL) للمفاتيح حيثما أمكن؛ فالرموز قصيرة العمر أكثر أمانًا من المفاتيح طويلة العمر
  • سجلات التدقيق: سجّل كل استخدام لمفتاح API مع الوقت وعنوان IP، واضبط تنبيهات للاستخدام غير المعتاد

نهج انعدام الثقة (Zero Trust): استخدم رموزًا قصيرة العمر (تدفق OAuth 2.0 client credentials) بدلًا من مفاتيح API طويلة العمر للخدمات عالية القيمة. فالرمز الذي تنتهي صلاحيته خلال ساعة واحدة يُحدث ضررًا أقل بكثير عند تسريبه من مفتاح صالح لمدة 90 يومًا.

مرجع سريع: ماذا تستخدم ومتى

  • إنسان يسجّل الدخول إلى تطبيق ويب ← كلمة مرور (مُجزّأة باستخدام Argon2) + MFA
  • الخادم الخلفي لديك يستدعي API لطرف ثالث ← مفتاح API في مدير أسرار، يُمرَّر عبر متغيرات البيئة
  • تطبيق الصفحة الواحدة (SPA) يستدعي خادمك الخلفي ← JWT قصير العمر (وليس مفتاح API)
  • خط CI/CD ينشر تطبيقك ← مفتاح API بأقل نطاق نشر ممكن
  • التحقق من توقيع webhook ← سرّ HMAC (وهو تقنيًا شكل من أشكال مفاتيح API)

ولّد مفتاح API أو سرًّا آمنًا

يولّد Zecure مفاتيح API آمنة تشفيريًا، وأسرار JWT، ومفاتيح AES-256 وغيرها، كلها داخل متصفحك، ولا تُخزَّن في أي مكان.
